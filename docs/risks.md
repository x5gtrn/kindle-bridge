# Risks — Obsidian Kindle Bridge

Status: updated after Phase 3 (Manual Sync MVP) implementation. Each risk has an id (R-NN) for cross-referencing from code comments/issues. Severity/likelihood are qualitative estimates based on the reference project's issue history (see `docs/architecture.md` §1, §13 research notes) and, except where noted below, are not empirically re-verified against a live Amazon account or a real Obsidian desktop install in this milestone - this codebase has been built, unit-tested (Vitest, with `electron`/`obsidian` unavailable in that environment), linted, and typechecked, but the Electron-`BrowserWindow`-dependent paths (sign-in, sign-out, session check, page fetch) have **not** been exercised end-to-end inside a running Obsidian instance. Anyone picking this up should manually verify those paths before relying on them.

| ID | Risk | Likelihood | Impact | Mitigation in MVP | Residual risk |
|----|------|------------|--------|--------------------|----------------|
| R-01 | Not an official/public API | High (certain) | High | Scrape only the rendered `read.amazon.<tld>/notebook` page a logged-in user could view themselves; no reverse-engineered private/mobile APIs; document this explicitly to users in README | Amazon can change or block this surface at any time without notice |
| R-02 | HTML structure changes break parsing | High — reference project has multiple open issues about broken/partial scraping as of 2026-08 | High | Parsers assert structural expectations and throw a typed `KindleParseError` surfaced to the user as "Amazon's page structure may have changed" instead of silently returning empty data (see architecture.md §5–6); parser fixtures + tests make regressions visible immediately when Amazon HTML samples are refreshed | No automatic self-healing; a break still requires a plugin update |
| R-03 | Amazon Conditions of Use may restrict automated access | Medium | Medium–High (account risk to end users, not to us as developers) | MVP only automates what a signed-in human already does manually (view own notebook, click through pages) via a real browser window with real navigation — no credential harvesting, no CAPTCHA bypass, no API reverse-engineering, strict rate limiting (§ request control in spec); README explicitly states this is unofficial/use-at-own-risk | We cannot guarantee Amazon won't rate-limit, challenge, or take action against automated-looking traffic even at low volume |
| R-04 | Session cookies / auth data mishandled | Medium if custom-coded, Low with chosen design | High (account compromise if leaked) | Cookies are never read, parsed, or persisted by plugin code — they live only in Electron's own `persist:` session partition (Chromium's native encrypted-at-rest cookie store); nothing auth-related is written to `data.json`, vault files, or logs (see architecture.md §4, and logging rules in the plugin spec) | If Obsidian's Electron sandboxing model changes, this assumption needs re-validation |
| R-05 | MFA | Medium (account-dependent) | Medium | Handled entirely inside Amazon's own login page rendered in the `BrowserWindow`; plugin does not detect, intercept, or special-case MFA — it just waits for the success-URL signal | If Amazon's MFA flow redirects outside the embedded window (see R-08/issue #337 pattern), login can stall with only a timeout as feedback in MVP |
| R-06 | CAPTCHA | Medium | Medium | Rendered natively inside the login `BrowserWindow`; user solves it like in a normal browser; plugin performs no bypass, solving service, or fingerprint spoofing (explicit non-goal) | Amazon may present CAPTCHA specifically in response to embedded-webview/automation heuristics more often than in a full browser; no mitigation planned beyond "let the user solve it" |
| R-07 | Regional differences (domain, locale, date formats, DOM variants) | Medium–High | Medium | MVP limited to exactly 2 well-understood regions (jp, global); region registry isolates domain/URL differences; date parsing is a single region-aware function, not scattered logic (architecture.md §3, §6) | Japan-specific date/locale quirks are only validated against fixtures we construct in Phase 2, not live-verified against every possible Amazon JP account state |
| R-08 | Obsidian/Electron sandboxing constraints on `BrowserWindow` / `electron.remote` | Medium | High (blocks the core auth mechanism) | Implemented in `src/amazon/electronRemote.ts`: `require("electron")` is called lazily (never at module load time) and wrapped in try/catch, so a missing/removed `remote` module degrades to a thrown `AmazonAuthUnsupportedError` instead of crashing the plugin. `AmazonAuthService`, `AmazonSessionService`, and `KindleReaderClient` all share this guard. **Not yet live-verified inside a real Obsidian desktop install** - Phase 0 research found the reference plugin's own `electron.remote.BrowserWindow` usage still functioning as of its last release (its one open related issue, #337, is Amazon redirecting to an external browser mid-login, not `remote` being unavailable), which is the basis for expecting this to work, but it has not been confirmed against this codebase specifically | If the guarded path is unavailable on the user's Obsidian version, MVP has **no working login** for that user — this is an accepted, documented limitation, not silently worked around. If it *is* available but behaves subtly differently than assumed (event signatures, timing), failures may surface as unexpected `navigation-error`/`timeout` results rather than success - needs real-world testing to tune |
| R-09 | Mobile (iOS/Android) not supported | High (certain, by design) | Low (explicitly out of scope) | `BrowserWindow`/Electron-based login and scraping only exist on Obsidian desktop; `manifest.json` should mark `isDesktopOnly: true`; README states mobile is unsupported | None planned for MVP; a mobile story (if ever pursued) requires an entirely different auth strategy (e.g. server-side proxy), out of scope for the foreseeable future |
| R-10 | Kindle annotations may lack a reliable creation timestamp | Medium (varies by annotation/region, per reference project's per-locale date-parsing hacks) | Low–Medium | `createdAt` is optional (`string | undefined`) in the `KindleAnnotation` model; renderer omits the "Created:" line when absent rather than fabricating a date; annotation ID generation falls back gracefully by only including date in the hash when present (see architecture.md §6) | Sort order / "last annotated at" on the book note may be less precise for annotations missing dates |
| R-11 | Highlight–Memo association may be unstable | Medium (reference project's own scrape path does not structurally separate the two; only their alternate My-Clippings parser does) | Medium | Parser treats a highlight and its associated memo as originating from the same structural block in the source HTML (matching how Amazon's page actually groups them) and models it as one `KindleAnnotation` with an optional `memo` field rather than trying to fuzzy-match two separate lists after the fact | If Amazon's markup ever separates highlight/memo into genuinely independent blocks, this association logic will need revisiting — covered by a dedicated parser test case per spec ("HighlightとMemoの関連付け") |
| R-12 | Cover image URLs may expire or be access-restricted | Low–Medium | Low | MVP never downloads or caches images locally (by design, per spec); it always stores/embeds the Amazon-hosted URL as-is; if a URL later 404s, the note simply shows a broken image — not a sync failure | No refresh mechanism for stale image URLs in MVP; would require a re-sync to pick up an updated URL if Amazon rotates it |
| R-13 | No deletion/diff detection in MVP | High (certain, by design — explicitly deferred to Phase 4+) | Low–Medium (data hygiene, not data loss) | Every sync only adds/updates annotations inside the generated block; annotations removed on Amazon's side are **not** removed from the note, so notes can accumulate content Amazon no longer has | Documented explicitly in README and `docs/mvp-scope.md` as a known MVP limitation; users relying on deletions being reflected must wait for Phase 4 |
| R-14 | Rate limiting / HTTP 429 from Amazon | Medium | Medium | Strict concurrency (1–2), inter-request delay, bounded retries only on transient errors, and an immediate full-stop (no retry) on 429 — sync ends with a clear "Amazon rate-limited this session" error rather than hammering harder | If 429 is hit mid-sync, already-fetched books are still saved (partial success), but the user must wait and retry later for the rest |
| R-15 | Reference project's `electron.remote` usage pattern is itself already fragile/deprecated | Medium | Medium | We do not port that pattern as-is; see R-08 mitigation | Underlying Electron API deprecation trajectory is outside this project's control |
| R-16 | HTTP 429 detection relies on an Electron `webContents` `did-navigate` event signature (`(event, url, httpResponseCode, httpStatusText)`) that is long-standing but not guaranteed across every Electron version Obsidian might bundle | Low–Medium | Medium (a missed 429 means the hard-stop-on-rate-limit requirement silently doesn't trigger) | `KindleReaderClient` reads `httpResponseCode` defensively (`typeof responseCode === "number"`) rather than assuming it's always present; a missing/different signature degrades to "429 not detected via this path" rather than throwing | Not live-verified; if Obsidian's bundled Electron uses a different event shape, 429s might only be caught indirectly (as a `TransientNetworkError` that keeps retrying up to `MAX_ATTEMPTS`, which is still bounded, just not an immediate hard stop) |
| R-17 | Amazon paginates a book's highlights/notes beyond a per-page limit; MVP's `KindleReaderClient.fetchBookAnnotationsHtml` fetches only the first page | Medium (matters for heavily-annotated books) | Medium (incomplete highlight/memo sets for those books, not a crash) | Documented here and in code comments (`KindleReaderClient.ts`); out of scope for this milestone alongside the reference project's own "max 54 books, no pagination" limitation on the book-list side | A future phase needs to follow Amazon's pagination tokens (see Phase 0 research notes on `.kp-notebook-content-limit-state` / next-page-start hidden fields) to fetch every page per book |
