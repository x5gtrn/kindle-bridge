# Risks — Obsidian Kindle Bridge

Status: updated after the MVP acceptance audit (see `docs/mvp-acceptance-report.md`). Each risk has an id (R-NN) for cross-referencing from code comments/issues. Severity/likelihood are qualitative estimates based on the reference project's issue history (see `docs/architecture.md` §1, §13 research notes) and, except where noted below, are not empirically re-verified against a live Amazon account or a real Obsidian desktop install in this milestone - this codebase has been built, unit-tested (Vitest, with `electron`/`obsidian` unavailable in that environment), linted, and typechecked, but the Electron-`BrowserWindow`-dependent paths (sign-in, sign-out, session check, page fetch) have **not** been exercised end-to-end inside a running Obsidian instance. Anyone picking this up should manually verify those paths before relying on them - see `docs/manual-test-checklist.md`.

**Audit follow-up (2026-08-06):** a self-audit before Phase 4 found and fixed two real defects that had been sitting in the code since Phase 3: `manifest.json`'s `minAppVersion` was `1.4.0` but the plugin calls `FileManager.processFrontMatter()`, which requires Obsidian `1.4.4`; and a 5-minute sign-in timeout wasn't cleared on plugin unload. Both are fixed (see `docs/mvp-acceptance-report.md` "Blocking Issues" for detail); they don't change any risk's likelihood/impact rating below, so R-01 through R-17 are otherwise unchanged.

**Real-world confirmation (2026-08-06, same day):** manual testing against a real Obsidian 1.13.4 install confirmed **two** issues predicted but not proven above:
1. A separate bug (not a risk materializing, a real defect) in `main.ts`'s `runSignIn()` silently swallowed the `AmazonAuthUnsupportedError` synchronous throw - fixed by switching to `await`/`try`-`catch` (matching `runSignOut`/`runSync`'s existing correct pattern).
2. **R-05 materialized as predicted**: after the fix above, sign-in still didn't complete - Amazon's login flow triggered a "new window" navigation that escaped the plugin's `BrowserWindow` into the user's system default browser, exactly the symptom documented in the reference project's issue #337 during Phase 0 research. The user could complete sign-in in the external browser, but the plugin's window (a separate, unrelated session/process) had no way to detect that or use it, leaving cancellation as the only option.

   **Mitigation added (round 1)**: `electronRemote.ts`'s new `keepNavigationEmbedded()` set `webContents.setWindowOpenHandler()` on every `BrowserWindow` this plugin creates (login, sign-out, session check, page fetch), forcing any new-window navigation to load inside that same window instead of escaping elsewhere.

   **Round 1 re-tested, still failed**: the reporting user rebuilt and retried with debug logging on. The console showed exactly one line - `Amazon login navigation {"origin":"https://www.amazon.co.jp"}` (the sign-in page loading normally) - then nothing further, no error, before the external browser opened. No second `did-navigate`, no `did-fail-load`, and (implicitly) the `setWindowOpenHandler` path from round 1 never logged an interception either. This is inconsistent with a `window.open()`/new-window escape (which round 1's fix would have caught and logged) and consistent instead with a **top-level navigation** (`will-navigate`) being vetoed and redirected externally by an app-level policy before it ever reaches this plugin's own `did-navigate` listener.

   **Mitigation added (round 2)**: `keepNavigationEmbedded()` also started listening for `will-navigate`, calling `event.preventDefault()` and reloading the same URL in the same window itself.

   **Round 2 re-tested, revealed the fix itself was harmful**: the debug log now showed three lines - the initial sign-in page load, a "kept embedded" interception, and a second successful `did-navigate` - confirming the `will-navigate` listener *was* firing and *was* successfully redirecting navigation back into the same window. But the user reported the window then bounced back to the **email entry step** instead of progressing, and the external browser still opened. Root cause: `will-navigate`'s `url` argument carries only the destination URL, never the original HTTP method or form body. Amazon's "Continue" step (after entering an email) submits as a POST; replaying only the URL via `win.loadURL(url)` downgrades it to a bare GET, which Amazon's server evidently rejects by bouncing back to the start of the flow. Worse, this happened *without* actually stopping the external-browser escape - strong evidence that whatever opens the external browser is independent of this plugin's own `will-navigate` listener (e.g. a separate, app-level listener on the same event that isn't affected by another listener calling `preventDefault()` - each listener's own side effects run regardless of what others do).

   Confirmed further by asking the user to bring the (still-open, just backgrounded behind the newly-opened external browser) plugin window to the foreground after triggering the escape: it was alive and had "some transition or reload" happening, consistent with the broken POST-to-GET downgrade above, not consistent with the window being closed/dead.

   Passkeys/WebAuthn were also ruled out as a contributing factor: the user removed all passkeys from their Amazon account and retested with no change in behavior.

   **Action taken (round 3)**: reverted the `will-navigate` interception entirely - `keepNavigationEmbedded()` now only handles `setWindowOpenHandler` (new-window requests, which have no request body to lose and are confirmed safe to replay). A new `observeTopLevelNavigation()` attaches a `will-navigate` listener that logs the target URL but never calls `preventDefault()`, so top-level navigation proceeds exactly as Electron would handle it unmodified - purely to gather more diagnostic signal without repeating the same mistake.

   **Round 3 re-tested with two independent findings.** First, with every other community plugin disabled, one test run failed at the very first `loadURL()` with `ERR_CONNECTION_REFUSED` (-102) - a transient/environmental network error unrelated to this investigation, resolved by simply retrying. Second, the actual retest (Kindle Bridge as the only enabled plugin, network working): the sign-in page loaded correctly, the user entered an email and clicked "Continue," `observeTopLevelNavigation()`'s log line fired (confirming `will-navigate` *does* fire for this navigation) - and the external browser still opened, while **the plugin's own window did not advance at all**, still sitting on the email-entry screen. Since this plugin's own listener no longer calls `preventDefault()` in this round, the fact that navigation still didn't proceed inside the plugin's own window means something *other than this plugin's code* prevented it - conclusive evidence the escape is caused by a listener or policy entirely outside this plugin's control, and ruling out any remaining "other installed plugin" explanation.

   **Independent, external confirmation**: the reference project's own GitHub issue #337 (Phase 0 research had already flagged this issue by title; re-checked in full during this investigation) describes the *exact* symptom - "the 'Continue' button after email login prompt doesn't get you to the password prompt page, instead it opens your browser (outside of obsidian) ... Obsidian remains in the email prompt page and can't login" - reported independently by multiple users (most recently 2026-08-06, the same week as this investigation), with the original report's metadata listing **Obsidian version: 1.13.4** - identical to the version used in all testing above. The issue remains open with no maintainer fix as of this writing. Obsidian's own 1.13 desktop changelog separately notes a fix to "clicking external links in pop-out windows causing the pop-out window to close," indicating Obsidian's core changed how secondary/pop-out Electron windows handle external-looking navigation around this version - plausibly the same code path affecting plugin-created `remote.BrowserWindow` instances, though this hasn't been verified against Obsidian's source directly.

   **Conclusion**: this is very likely a genuine, current limitation of the `electron.remote.BrowserWindow`-based sign-in approach on Obsidian ~1.13.x, external to this plugin's own code, affecting at least one other, more mature and widely-used plugin using the same approach. Further speculative `webContents`-level navigation interception is not expected to help, since the escape has now been shown to happen independent of anything this plugin's own listeners do. This is documented as a known, currently-unresolved blocker for the "Sign in to Amazon" feature on affected Obsidian versions - see `docs/mvp-acceptance-report.md` for how this affects the MVP acceptance status.

   **Design change attempted (2026-08-07)**: since the escape appears specific to *separate windows* (`remote.BrowserWindow` instances, which Obsidian's core may treat differently from its own window for navigation purposes - Obsidian's own 1.13 changelog separately notes a fix to external-link handling specifically in "pop-out windows"), `AmazonAuthService.signIn()` was rewritten to render Amazon's login page inside an Electron `<webview>` element embedded directly in an Obsidian `Modal` - i.e. inside Obsidian's own window - instead of a separate `BrowserWindow`. See `docs/architecture.md` §4 for the implementation.

   **Retested same day, ruled out**: the `<webview>` element never fired `dom-ready` within the 15-second capability-detection timeout, so `signIn()` failed closed exactly as designed - a clear `AmazonAuthUnsupportedError` Notice, no dangerous fallback, no crash. Console: `Amazon sign-in: <webview> never became ready; treating as unsupported`. This means the hosting window (Obsidian's own) does not have `webviewTag: true` enabled - a setting only Obsidian's core controls, not something a community plugin can turn on - so embedded `<webview>` is not a viable path on this installation either.

   **Status after five rounds of live investigation**: both realistic embedding mechanisms available to a community plugin - a separate `remote.BrowserWindow` and an embedded `<webview>` - have now been tried and ruled out, for two different underlying reasons (an external navigation policy this plugin cannot override, and `webviewTag` not being enabled, respectively). No further embedding technique is known to be available from within Obsidian's community plugin API surface. The remaining realistic options all require a genuine design decision rather than another code-level attempt:
   1. **Accept external-browser sign-in as the primary flow and design a session-handoff mechanism** so the plugin can use a session established in the user's regular browser. The user has already demonstrated they *can* complete Amazon sign-in in their external browser without issue - the gap is purely that this plugin currently has no way to use that session, since Electron's `persist:` partition and the system browser's cookie store are entirely separate. Any concrete design here needs to be scoped carefully against this project's "never handle passwords/OTP/cookies carelessly" principles before implementation - not something to build unilaterally.
   2. **Wait and monitor** the reference project's issue #337 and Obsidian's own release notes for any upstream change that resolves the underlying navigation-policy behavior.
   3. **Accept the current limitation** and ship the MVP with "Sign in to Amazon" documented as non-functional on affected Obsidian versions, revisiting later.

   **Design change implemented (2026-08-07, sixth attempt)**: rather than any of the three options above, the underlying premise - that sign-in must happen *inside* an Obsidian/Electron-managed window at all - was dropped. `electron.remote` (and the `<webview>` tag) are no longer used anywhere in this plugin. `AmazonAuthService`, `AmazonSessionService`, and `KindleReaderClient` were all rewritten to drive a genuinely separate Chrome/Edge/Chromium/Brave process via a hand-rolled Chrome DevTools Protocol (CDP) client (`src/amazon/cdp/`), launched with `child_process.spawn()` and a persistent `--user-data-dir` outside the vault (see `docs/architecture.md` §4 for the full design). Because this process has no relationship to Obsidian's own `webContents`/window policies at all, the external-navigation-escape behavior documented in rounds 1-3 above cannot apply to it by construction - there is no "top-level navigation being redirected out of an embedded window" to escape from, since the window was never embedded in the first place. This also resolves R-08 as originally framed (`electron.remote` availability is no longer a dependency of the auth path at all) and drops the reference project's own fragile-API-pattern risk (R-15).

   An `playwright-core`-based approach was considered and rejected first: a bundling spike proved `playwright-core` cannot be flattened into this plugin's required single-file `main.js` (its own source does `require()` calls with `__dirname`-relative paths, e.g. to read its own `package.json`, that don't survive esbuild bundling - confirmed by actually building and running it, not just inferred). Auto-downloading a dedicated Chromium at first run was also considered and rejected, since it would change the plugin's distribution/footprint model, which was explicitly ruled out. The hand-rolled CDP client avoids both problems: it adds no new npm dependency (only Node builtins - `child_process`, `node:fs`/`node:os`/`node:path`, the native `WebSocket` global) and requires no change to the single-`main.js` distribution model.

   **Trade-off accepted**: this approach requires the user to have a compatible browser (Chrome, Edge, Chromium, or Brave) already installed on their machine; if none is found, `signIn()`/`isSessionValid()`/`fetchBookListHtml()` all fail closed with `AmazonAuthUnsupportedError` (see `BrowserNotFoundError` in `src/amazon/cdp/browserExecutable.ts`), matching this project's established "fail closed with a clear error, never a silent/dangerous fallback" principle. The sign-in UX also changed: instead of an in-app modal, a real, separate browser window opens for the user to complete sign-in in, then the plugin detects success by polling the window's URL against the region's reader URL.

   **Not yet live-verified**: this implementation is new as of 2026-08-07 and, unlike the `remote.BrowserWindow` and `<webview>` attempts above, has not yet been tested against a real Obsidian install or a real Amazon account - only unit-tested (with `CdpBrowser` mocked) and confirmed to bundle correctly into `main.js` without the path-resolution failure `playwright-core` had. The next manual-testing round should confirm: (a) browser discovery finds an installed browser on the tester's machine, (b) the separate browser window actually opens and is usable, (c) success detection correctly fires once the user reaches the notebook/reader page, (d) the persistent profile directory carries the session across subsequent headless launches (session check, page fetch) without requiring the user to sign in again each time.

   **Live testing, round one (2026-08-07, same day)**: found and fixed two real defects, in order:
   1. `CdpBrowser.launch()` failed with "Browser exited before becoming ready (code 0)" and, once stdout capture was added for diagnosis, the browser's own explanation: `Opening in existing browser session.` Chrome was handing the launch off to an already-running process instead of starting a new, controllable one - not because the user's regular browser was open (ruled out by testing with it fully quit), but because `launch()` itself leaked a Chrome process on an earlier failure: it never killed the just-spawned process if a step *after* the process had already started (connecting to its DevTools WebSocket) subsequently failed, leaving that process alive forever, holding the profile directory's singleton lock. Fixed by wrapping post-spawn steps in try/catch and killing the process before rethrowing on any failure.
   2. With that leaked process cleared out, launching failed differently: Chrome started correctly and printed its DevTools URL, but connecting to it failed outright (`Could not connect to ws://127.0.0.1:.../devtools/browser/...`). Root cause: Obsidian's plugin code runs in an Electron renderer process with a Content-Security-Policy that blocks the DOM `WebSocket` global from connecting to arbitrary `ws://` origins - the same restriction Obsidian's own API works around for HTTP by providing `requestUrl()` instead of `fetch()`. Fixed by adding `cdp/NodeWebSocket.ts`, a minimal RFC 6455 client hand-rolled on Node's `net` module instead of the DOM `WebSocket`, which isn't subject to the renderer's CSP. See `docs/architecture.md` §4.

   Both fixes are implemented and unit/integration-tested (`NodeWebSocket.spec.ts` runs the handshake and frame protocol against a real, independently-implemented TCP test server, not just against its own internals).

   **Confirmed working (2026-08-07, same day)**: sign-in completed end-to-end against a real Amazon account (co.jp) after the two fixes above - the separate browser opened, the user completed login, and the plugin detected success (`Amazon sign-in navigation {"origin":"https://read.amazon.co.jp"}`) and returned control to Obsidian. This resolves the "not yet live-verified" status for the CDP-based sign-in mechanism itself. `Sync now` afterward surfaced further, separate issues in the sync path - see R-02 below and the "Live testing, round two/three" entries there.

**R-02 materialized (2026-08-07), round two of live testing**: with sign-in working (R-05 above), the first full `Sync now` completed - `Books found: 9`, `Errors: 0` - but every single book was skipped, with `Highlights fetched: 0` and `Memos fetched: 0`. Since `errors: 0` ruled out `KindleAnnotationParser` throwing `KindleParseError`, the annotations *container* (`#kp-notebook-annotations`) was being found; its children weren't matching. Initial hypothesis (added defensively, see `docs/architecture.md` §4/§5): per-book content might render asynchronously after `load`, unlike the book list - added `CdpPage.waitForSelector()` to wait for an annotation to actually appear before snapshotting. Retesting still showed 0 for every book, with debug logs showing `No annotations rendered within timeout` for all nine.

**Round three - confirmed via direct DOM inspection on the live account**: rather than guess further, had the user open a book's annotations URL directly in their regular browser and inspect the real DOM via `document.querySelector('#kp-notebook-annotations').children[...]`, redacting actual highlight/memo text (only tag/class/id structure was needed). This confirmed the *actual* root cause: **every per-item selector this parser shipped with was already stale and never matched anything** - `.kp-notebook-annotation`, `.kp-notebook-highlight-text`, `.kp-notebook-note-text`, `.kp-annotation-location`, `.kp-annotation-page`, `.kp-annotation-created` don't exist in Amazon's current markup. The container ID (`#kp-notebook-annotations`) happened to still be correct, which is exactly why this surfaced as "0 results, no error" instead of a `KindleParseError` - the resilience contract below only guards against the *container* going missing, not against per-item selectors silently matching nothing. Real annotations are `div`s with a generated `id` and Amazon's generic `a-row a-spacing-base` classes; highlight text is `#highlight`, memo text is `#note`, location is `#kp-annotation-location`'s `value` attribute (an `id`, not a `class`). **Also confirmed: the current markup exposes no page number and no per-annotation date at all** - both fields are now always `undefined` (see `docs/architecture.md` §6). `KindleAnnotationParser.ts` and its fixtures were rewritten to match; not yet re-verified against a live account after this fix.

This is a concrete illustration of this row's own "no automatic self-healing" residual risk playing out in practice - it went undetected through Phase 2's fixture-based tests because those fixtures were themselves guesses (not captured from a real account), and undetected by the resilience contract because a *structurally valid but semantically empty* result looks identical to "this book genuinely has no highlights" from the container-existence check alone.
